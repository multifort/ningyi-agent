# 多智能体平台 — 架构设计基线

> 本文是设计讨论的沉淀，**只描述架构（是什么/为什么/职责/数据/流程/待定/风险），
> 不涉及实现节奏与 MVP 拆解**（按约定，整体理清前不谈落地）。
> 这是一份"活文档"，随讨论推进更新。最后更新：2026-06-09（第五轮：对标市面多 agent 系统，新增第 9 节"缺口补强 7 条"）。

---

## 0. 目标与背景

在现有"宁翼智能（chat + agent 双模式，agent 由 hermes CLI 驱动）"之上，演进为一个
**可定义角色 / 可编排协同 / 可自动规划** 的多智能体平台。用户通过它把系统性任务
（如"做一份竞品调研报告"）交给多个定制 AI 角色协作完成。

设想的三层（用户原话归纳，本轮细化）：
- **第一层 角色（按意图编配，不是手工建角色）**：onboarding 问答理解用户场景/偏好 →
  **角色编配器** 匹配场景预设、组装预设角色、对缺口自动生成角色 → 落进一个【组织/虚拟公司】。
- **第二层 多角色协同**：一个组织内的多个角色围绕同一任务协作，共享数据；通信与调度由协同层负责，角色只执行。
- **第三层 任务规划**：用大模型把系统性任务拆解（任务-规范-计划等维度），交给第二层调度第一层执行。

执行链路自上而下：**规划层拆任务 → 编排层分派 → 角色层执行**。

### 顶层容器：组织 / 虚拟公司（Org）—— 本轮新增
把"某场景下的所有角色 + 共享资源 + 治理"统一装进一个 **Org（虚拟公司 / 工作区）**：
```
用户(账户)
  └─ 组织 / 虚拟公司 (Org)        ← 一个场景一个；多租户/计费/治理/记忆 的单位
       ├─ 角色花名册              ← 编配器产出的角色组（这家公司的"员工"）
       ├─ 组织级共享资源          ← 共享工作区 / 知识库 / 已连模型+凭证 / 预算
       ├─ 组织级记忆              ← 跨任务持久（公司的积累）
       ├─ 策略/权限/审批/预算      ← 治理
       └─ 任务 (Tasks)           ← 在公司里跑，走 规划→编排→执行
```
> **重要界定**：这个"公司"是 **管理/资源/身份/治理的边界，不是执行时的层级**。
> 角色之间仍不直接对话；"管理者/老板"落地是 **planner + Temporal**，不是一个 LLM 老板 agent。

## 1. 三条核心设计原则

这三条贯穿全局，是后面所有组件设计的根。

### 原则一：角色（配置） 与 执行器（运行时） 解耦
- **角色 = 一份廉价的配置数据** `{系统提示词 + 技能集 + 工作目录 + 可用能力}`，可以无限多。
- **需要容器化、需要扩容的是执行器**，做成一个 **Worker 池**（横向多副本）。
  **执行器是可插拔接口，不绑定 hermes**（hermes 偏重，仅作可选档）。
- **并发度 = Worker 副本数**，绕开单进程不能并发的限制（不需要它并发，多开即可）。
- 推论：**不是"每个角色一个常驻容器"**（那样空闲角色白占资源），而是"任意角色配置丢给任意空闲 Worker 执行"。

### 原则二：Worker 无状态，状态全部外部化、运行时注入
- 每次角色执行 = 启动 → 读外部状态 → 干活 → 写回 → 进程销毁；可随时杀/重试/换 Pod。
- **运行时注入给无状态 Worker 的三样东西**（完全对称）：
  1. **上下文切片**（这次该知道的全局上下文）
  2. **启用的 skills**（这个角色声明要用的技能）
  3. **模型配置 + 凭证**（按能力解析出的模型 + 用户的临时密钥）
- 好处：重试、并行、换 Worker 都不需要"会话黏在某个 Pod 上"，可靠性高。

### 原则三：目标每步在场（目标一致性）
- 任务的"目标 + 验收标准"不可变，**注入到每一个角色的上下文切片里** = "北极星"。
- 每步产出在并入全局上下文前，可由门禁（校验/审核角色）对照验收标准放行。

> **执行器（运行时）是可插拔接口，hermes 只是其中一档、且非默认。**
> 因为 skill 是 Markdown 手册、与运行时无关，**同一个 skill 在任意执行器上都能跑（无锁定）**。
> 档位（角色按需声明）：
> - `pure-llm` —— 纯推理，一次模型调用，最轻（审核/校正这类）
> - `lite-agent`（**默认**）—— 轻量自研循环：注入 skill 手册 + 模型原生 tool-calling + 极小工具集
> - `media` —— 媒体生成（图/视频）
> - `hermes` —— 仅在确需其特定能力时备用（偏重；甚至可不用）
> 取舍：短期 hermes 上手快；长期 lite-agent 更轻、更可控（代价：自研 agent 循环+工具执行+安全）。

## 2. 整体分层与组件

```
入口：onboarding 问答 → 角色编配器（匹配场景预设 / 组装 / 缺口生成）→ 建并填充 组织(Org)
        │
组织(Org 虚拟公司)：角色花名册 · 组织记忆 · 启用技能子集 · 凭证/预算 · 治理策略 · 共享工作区
        │  （任务在 Org 内执行；下面是各 Org 共用的平台能力）
控制面(宁翼 server 升级)：角色注册表 | 场景预设库 | 模板库 | 规划器 | 人审 UI | 公司看板
        │
编排层：Temporal（DAG 执行、重试、人审暂停、运行中 signal 干预、缺失 skill 子工作流）
        │
   ┌────┴───────────────────────────┐
Context Manager(上下文管家)        Skill 库
 持有全局上下文/切片/收信封/出处     注册·版本·信任·检索 + 自动生成 + 验证沙箱
        │                               │
执行层(可插拔 Executor)：lite-agent(默认) | 纯 LLM | 媒体生成器 | hermes(可选备用)
        │
Model Router(能力路由)：系统模型目录 + 每用户凭证保险库 → 按需注入 → 各家模型后端
        │
数据面：每任务一个共享卷(任意模态产物) + DB(产物描述符台账, 结构化 + JSONB)
```

### 组件职责
| 组件 | 职责 |
|---|---|
| **角色编配器(Role Provisioner)** | onboarding 意图 → 匹配场景预设 / 组装预设角色 / 缺口自动生成 → 建并填充 Org（生成角色需人审） |
| **场景预设库** | 命名场景打包 `{默认角色组 + 技能 + 默认计划模板}`，版本化；供编配器检索 |
| **组织(Org/虚拟公司)** | 角色花名册 + 组织级资源(工作区/知识/凭证/预算) + 组织记忆 + 治理策略；多租户/计费/隔离的单位 |
| **公司看板(可观测)** | 消费 Temporal/Context Manager 的状态事件，展示"哪个角色在做什么/进度/已花成本/卡点" |
| **角色注册表** | 存角色配置（提示词+技能+可用能力+执行器档位+最小权限+角色记忆引用+版本） |
| **模板库** | 预先写好的 Plan（DAG 模板），版本化管理 |
| **规划器** | 目标 → Plan(DAG)；混合式：检索模板→LLM 填充/微调，否则 LLM 全自动拆解 |
| **人审 UI** | 计划确认、审核断点、运行中干预、成本可见 |
| **编排层(Temporal)** | 按 DAG 调度、并行/串行、重试、人审暂停(signal)、缺失处理子流程 |
| **Context Manager** | 持有全局上下文；给每个角色切片；收"结果信封"；维护有界台账与出处 |
| **Skill 库** | skill 的注册/版本/信任/检索；缺失时检索或自动生成 + 验证沙箱 |
| **执行层** | 可插拔 Executor：**lite-agent(默认,轻量自研循环)** / 纯 LLM(推理) / 媒体生成器 / hermes(可选备用)；skill 与运行时无关 |
| **Model Router** | 系统模型目录；按"能力+预算"解析出模型 + 声明式 HTTP 连接器配置 |
| **Credential Broker** | 凭证保险库（信封加密、后端可插拔）；发任务级短时句柄、注入无状态 Worker、用完即焚、审计 |
| **数据面** | 共享卷存任意模态产物；DB 存结构化描述符台账 |

## 3. 关键数据模型（草案）

### 3.1 角色（Role）
```
{ id, orgId, name, version, systemPrompt,     // 归属某 Org；配置版本化、可回滚
  skills: [ "name@version", ... ],     // 扁平自包含、无依赖树（规划器只见平行 skill 集）
  availableCapabilities: [ ... ],        // 受控词表中的能力
  executor: lite-agent | pure-llm | media | hermes,   // 可插拔，默认 lite-agent；hermes 仅备用
  authority: {                           // 最小权限（在 Org 策略内）
    allowedTools: [ ... ],
    dangerousActions: 强制人审 },          // 发布/外发/支付等真实副作用 → 必走人审 gate
  roleMemoryRef,                          // 角色级记忆（跨任务积累，见 3.11 三层记忆）
  source: preset | generated | user-custom }   // generated 需人审才生效
```

### 3.2 计划（Plan / DAG）— 模板与 LLM 产出统一成同一 schema
```
{ goal, acceptanceCriteria,
  nodes: [
    { id, role, deps: [ids],
      executor: lite-agent | pure-llm | media | hermes,
      requiredCapabilities: [ ... ],     // 受控词表；用于匹配 skill / 模型 / 发现缺口
      inputHint, expectedOutput }
  ] }
```
- **模板** = 预先写好的 Plan（可带占位槽）。
- **LLM 拆解** = 输出同一 schema。下游执行器不关心计划来自模板还是 LLM。
- 串行/并行由 `deps` 依赖边决定（动态，由规划结果确定）。

### 3.3 产物描述符（Artifact Descriptor）— 多模态统一
```
{ id, taskId, nodeId,
  modality: text | image | video | dataset | ...,
  uri,                 // 指向产物存储（共享卷/对象存储），不是字节本身
  mime, caption,        // 文字摘要：注入上下文用这个，不注入字节
  provenance,           // 出处（源 URL + 抓取时间等）
  meta: JSONB }          // 模态专属字段（分辨率/时长…），统一结构化外壳 + 灵活内核
```
> 不在"结构化/非结构化"里二选一：**描述符永远结构化（行 + JSONB），内容任意模态存外部**。

### 3.4 结果信封（Result Envelope）— 每个角色干完产出
```
{ role, nodeId, status,
  artifacts: [ {path/uri, kind} ],
  facts: [ {claim, sourceUrl, retrievedAt, confidence} ],   // 关键事实 + 出处
  summary,              // 一句话：做了什么、结论是什么（进有界台账）
  needsHuman?: bool }
```

### 3.5 注入给角色的上下文切片（Context Slice）
```
{ goal + acceptanceCriteria,   // 北极星，不可变
  planPosition,                // DAG 位置 + 上游给了什么
  contextLedger,               // 累积事实(带出处)+各步摘要，体量受控
  workspacePaths,              // 可读文件清单
  roleInstruction }            // 本角色具体职责
```

### 3.6 Skill 包（与 hermes 现状一致）
- 形态：`skills/<name>/SKILL.md`（+ 可选 `references/`）。**是 Markdown 操作手册，不是代码**。
- frontmatter 现成字段：`name / version(semver) / description("When to Use" 触发条件) / metadata.hermes.tags / category`。
- 库要补的社区维度：`publisher / trust(信任档) / review_status / permissions(声明会用的工具/权限)`。
- 启用：共享卷只读挂载整个 skill 目录；角色声明 `skills:[name@version]`；hermes 用 `-s` 启用子集。

### 3.7 模型目录 与 用户凭证
```
模型目录(系统托管，无密钥)：
  { modelId, provider, capabilities: [受控词表], contextWindow, pricing,
    connector: {                       // 声明式 HTTP 连接器配置（默认路径）
      endpoint, authType, requestTemplate, responseParsePath, streamMode },
    adapter?: 长尾逃生口(异步视频/签名鉴权等才需要) }
用户凭证库(BYO，加密隔离，经 Credential Broker 访问)：
  { userId, modelId, credential(信封加密密文), quota/budget }
```

### 3.8 组织 / 虚拟公司（Org）
```
{ id, name, ownerUserId, charter(使命/范围),
  members: [ {userId, role:owner|approver|member} ],   // 先单 owner+审批人；留多成员位
  roles: [ roleId... ],                  // 角色花名册
  enabledSkills: [ "name@version"... ],   // 从全局 Skill 库"安装"的子集
  modelsScope, credsScope, budget,        // 组织级 BYO 凭证 + 预算
  orgMemoryRef,                           // 组织记忆（跨任务持久）
  sharedSchema,                           // 组织内共享术语表/产物 schema（保交接一致）
  policies,                               // 权限/审批/预算/数据隔离策略
  sharedWorkspace }                        // 组织级共享空间（任务级目录在其下）
```
> **数据隔离**：Org 间的工作区/记忆/知识严格隔离（多租户）。

### 3.9 场景预设（Scenario Preset）
```
{ id, name, version, description,
  roleTemplates: [ ... ],       // 这个场景默认有哪些角色（含提示词骨架+技能）
  defaultPlanTemplates: [ ... ], // 默认计划模板
  requiredCapabilities: [ ... ] } // 需要装哪些技能/能力
```

### 3.10 运行清单（Run Manifest）— 每个任务落一份，保可复现/可审计
```
{ taskId, orgId, startedAt,
  rolesUsed:  [ {roleId, version} ],
  skillsUsed: [ {name, version} ],
  modelsUsed: [ {modelId, version} ],
  planVersion, planSnapshot }
```
> 没有它，"这次为什么产出这个 / 为什么变差了"无法回答。

### 3.11 三层记忆
- **任务记忆**：单任务的短时台账（Result Envelope 累积，任务结束即归档）。
- **角色记忆**：某角色跨任务积累的标准/经验（如审核角色记住公司审稿口径）。
- **组织记忆**：公司级共识，跨任务跨角色（公司的积累）。
- 注入上下文切片时按需取这三层——**仍是摘要不是字节**，体量受控。
- **检索机制**：记忆向量化 + 按相关性 RAG 检索后注入（见 9.6），组织记忆越长越靠检索而非全注入。

## 4. 几条关键流程

### 4.0 角色编配 → 建组织（onboarding 入口）
```
onboarding 问答（想做什么 / 偏好）
  → 意图理解
  → 匹配【场景预设】：
       命中     → 实例化该场景角色组（按偏好微调提示词/技能）
       部分命中 → 用预设角色 + 对缺口自动生成角色
       不命中   → 自动生成一组角色
  → 生成的角色：预览 + 小样例验证 + 人审 才生效（意图会被 LLM 误读，必须确认）
  → 建并填充一个【Org 虚拟公司】：花名册 + 启用技能 + 共享工作区 + 组织记忆
  → 之后所有任务都在这家公司里跑
```

### 4.1 规划 → 人审 → 执行（在某个 Org 内）
```
用户目标
  → 规划器：检索模板库找最匹配 → 命中则 LLM 填槽/微调；不命中则 LLM 全自动拆解
  → 产出 Plan(DAG)，每节点标 requiredCapabilities
  → 【人审断点】用户确认/修改 DAG + 看到预估模型成本 + 设预算上限
  → Temporal 执行：按 deps 串/并行派给 Worker
       每步：Worker 读上下文切片 → 干活 → 写工作区 + 产出结果信封
             → Context Manager 更新台账（事实+出处+摘要）
  → 运行中可发 signal 暂停/改计划/重派（人随时干预）
```

### 4.2 缺失 skill 处理闭环（前期"先记待办"，不自动触发生成）
```
规划器标 requiredCapabilities → 语义匹配 skill 库 description
  命中 → 启用
  未命中 = 能力缺口
    → 生成【Skill 需求规格】{ 要解决的能力, 触发条件, 期望输入/输出, 约束/权限 }
        （一物两用：检索的查询 + 生成的任务书）
    → ① 检索社区/库（有则按来源定信任档拉回）
       ② 自动生成（"Skill 作者角色"按规格写 SKILL.md）—— 因为是 Markdown，生成可行
    → 验证沙箱（先用断言：样例输入 + 期望输出，在受限工具权限下真跑一遍）
    → 人审 → 通过才升信任档入库
  ⚠ 难点不是"生成"是"验证"；自动生成的 skill 默认落最低信任档，跑通验证+人审才升档。
  ⚠ 前期策略：缺口先记成待办，由人决定要不要补（不自动拖慢任务）。
```

### 4.3 模型按需注入 + 凭证隔离（BYO-Key，用户付费）
```
节点声明需要的能力(如 image-generation)
  → Model Router 按 { 能力满足 + 用户预算/偏好 } 在"用户已连接的模型"里选一个
     （够用就选便宜的，成本感知）
  → 取该用户凭证 → 以"任务级短时凭证"注入 Worker（仅本次调用存在）
  → Worker 调模型 → 用完即焚（凭证永不落盘/进日志/进上下文台账）
  → 记录用量（用户可见，用于他自己的计费）
  缺凭证 = 能力缺口 → 提示用户去连模型/选替代，不静默失败
```

### 4.4 多角色返工 / 分歧闭环（接缝处，质量命门）
```
审核角色对照验收标准判定上游产出
  通过 → 进入下一节点
  打回 → 退回上游角色重做（带具体修改意见）
       → 重试封顶 N 轮（防死循环）
       → 仍不过 → 升级人审（人决定：放行/再改/终止）
⚠ 触发条件、最大轮数、升级路径必须显式定义；否则多角色协作会在这里失控或空转。
```

## 5. 组织化与多角色治理（本轮新增：编配 + Org + 10 条考量）

> 这一节是本轮补的"组织化"设计，把角色编配、虚拟公司、以及多角色协作带出的 10 条考量收拢在一起。

### 5.1 角色编配（意图驱动，非手工建角色）
- 流程见 4.0。**生成的角色与生成 skill 同等兜底**：预览 + 小样例验证 + 人审才生效。
- 冷启动期预设少、生成多，质量更要盯；意图理解本身是 LLM 步骤，会误读 → 必须确认/可迭代。

### 5.2 组织（Org / 虚拟公司）
- 见第 0 节层级 + 3.8 数据模型。**是管理/资源/身份/治理边界，不是执行拓扑**；管理者=planner+Temporal，非 LLM 老板。
- **数据隔离**：Org 间工作区/记忆/知识严格隔离（多租户）。

### 5.3 多角色协作语义（接缝处）
- **角色集内聚**：编配产出的角色组要**职责不重叠、不漏**；Org 定义 **共享 schema/术语表**，否则文件交接对不上。
  进一步：把场景的角色交接固化为**强 schema 的 SOP**（9.7，MetaGPT 教训：质量来自 SOP+结构化产物，而非人设）。
- **返工/分歧闭环**：见 4.4（触发/轮数/升级显式定义）。

### 5.4 三层记忆
- 见 3.11：**任务记忆 / 角色记忆 / 组织记忆**；切片按需取，仍是摘要不是字节。

### 5.5 权限 · 治理 · 安全
- **每角色最小权限**：在 Org 策略里声明每个角色能用哪些工具；**带真实副作用的动作（发布/外发/支付）强制人审 gate**，不全自动。
- 这是对"被检索内容 prompt 注入操纵 带工具+带凭证 agent"的关键防线（与第 8 节风险呼应）。
- **预算执行**：Org/任务级预算硬上限 + 告警 + 超预算行为（暂停/询问）。

### 5.6 可观测与可复现
- **公司看板**：Temporal/Context Manager 吐状态事件 → 看板展示（谁在做什么/进度/已花成本/卡点）。可借鉴 DeskClaw 的 Cyber Workspace。
- **运行清单(Run Manifest)**：见 3.10，每任务落用到的版本，供审计/调试/回归。

### 5.7 生命周期与边界（先给方向，留数据位）
- **Org 演进**：角色配置版本化、可回滚；场景预设升级"提示但不自动套用"已建 Org。
- **人的位置**：MVP 单一 owner+审批人；数据模型给"多真人成员+权限"留位（见 3.8 members）。
- **Org 粒度**：先"一 Org 一场景"；多职能公司后置。

## 6. 已确定的决策

- **执行/角色**：角色=配置非容器；Worker 池横向扩容；**执行器可插拔接口**——默认 **lite-agent(轻量自研循环)**，
  另有 纯LLM / 媒体 / hermes(偏重·仅备用)；**skill 是 Markdown、与运行时无关（无锁定）**。
  工具走 **MCP**（9.4）：skill 讲"怎么做"、MCP 提供"用什么做"，自研工具仅在 MCP 没有时才写。
- **状态**：Worker 无状态；状态两层外部化（共享卷存产物 + DB 存结构化台账）；目标每步在场。
- **编排**：用 **Temporal**；编排者拓扑（角色**默认**不直接对话，通信调度由编排层做）；串/并由 DAG 决定。
  补：提供**受控交接/提问原语**（9.2，仍经编排层）；节点失败/产出不达标可触发**有界局部重规划**（9.1）。
- **数据共享**：共享任务工作目录（文件级），不走消息总线；上下文进 DB（描述符结构化 + JSONB，字节存外部）。
- **规划**：模板 + LLM 自动拆解都要，统一成同一 Plan schema，混合式规划；人审在"计划确认 + 审核"且可中途干预。
- **数据源（示例任务）**：互联网检索（强制带出处，是"数据准确"最脆的一环）。
- **Skill**：独立 skill 库（社区取可信 + 考虑自动生成）；skill=版本化 Markdown 手册非代码。
  - **扁平自包含、无依赖树**：规划器只见平行 skill 集，不做依赖解析（保持规划器简单可靠）。
  - **包 = SKILL.md + references/(随包的可用资料) + 声明的资源/权限需求**。
  - **发布强制人审**：提交 → 自动检查 → 人审 → 定信任档 → 上架（实现后置，包模型现在定）。
  - 信任分级（官方/已验证发布者/社区/私有，低档限权/需人审）；前期只组合，缺口先记待办。
- **Skill 验证**：**断言(客观) + LLM-as-judge(主观质量) 作过滤器**；**人审=信任档升级的终审**（judge 会判错，非终审）。
- **能力词表**：受控词表打底 + 语义匹配兜底（规划/skill/模型/路由全靠它对齐）。
- **模型层（BYO-Key、用户付费）**：系统托管模型配置、Worker 按能力按需加载；成本感知 + 成本在人审透明。
  - **模型后端 = 声明式 HTTP 连接器**（默认路径）：每模型一份配置
    `{endpoint, authType, requestTemplate, responseParsePath, streamMode}`，通用连接器组请求/调用/解析。
    覆盖标准同步 + SSE 流式文本、标准图像生成。
  - **薄适配器逃生口**（长尾）：异步媒体(视频:提交→轮询→取结果)、签名鉴权(SigV4/OAuth)、
    SSE 格式差异、多模态负载编码。即"**配置为主 + 少量适配兜底**"。
- **凭证保险库 = Credential Broker（OS 无关、可插拔后端）**：
  - **信封加密**：凭证用 DEK 加密，DEK 用 KMS 主密钥加密；DB 只存密文。
  - **后端可换**：生产/k8s 用 Vault 或云 KMS（Vault Agent/Secrets Store CSI 注入，tmpfs 内存、短 TTL、任务结束即销毁）；本地开发用加密文件/sqlite（同接口降级）。
  - Worker 只拿**任务级短时句柄**；凭证永不落盘/日志/上下文；每次取用审计。
- **角色自由生成边界**：前期只"选已有 skill + 生成系统提示词"；"生成全新 skill"为后续高级能力且需人审。
- **角色入口 = 意图编配，非手工建角色**：onboarding → 角色编配器（匹配场景预设 / 组装 / 缺口生成）→ 建 Org；生成角色需预览+验证+人审。
- **组织(Org/虚拟公司)为顶层容器**：一场景一 Org，是多租户/计费/治理/记忆/数据隔离的单位；它是**管理边界非执行拓扑**，管理者=planner+Temporal。
- **多角色协作语义**：角色集需职责不重叠/不漏 + Org 共享 schema；返工有"重做封顶 N 轮 → 升级人审"的显式闭环。
- **三层记忆**：任务 / 角色 / 组织；切片按需取摘要。
- **权限治理**：每角色最小权限；**真实副作用动作（发布/外发/支付）强制人审**；Org/任务级预算硬上限。
- **可观测+可复现**：公司看板（状态事件）+ 每任务 Run Manifest（角色/skill/模型/计划版本）。
- **部署目标**：服务器/云，k8s 容器集群承载（先在 Mac 验证——具体节奏本文不展开）。

## 8. 重点风险（设计阶段就要正视，不能后补）

1. **互联网数据准确性**：网页过时/矛盾/SEO 垃圾/诱发幻觉。对策：每条事实带出处+时间、关键结论多源交叉验证、
   矛盾标记而非硬合并、审核角色明确核对引用与时效。
2. **共享 Worker 池的凭证隔离**：A 的任务绝不能拿到 B 的密钥。对策：加密存储 + 任务级短时下发 + 用完即焚 +
   永不落盘/日志/上下文。做不好就是重大数据事故。
3. **自动生成 skill 的质量与安全**：真正的难点是验证而非生成。对策：验证沙箱 + 默认最低信任档 + 受限权限 +
   人审升档；否则库会被低质量/有注入风险的 skill 污染。
4. **递归自造 skill 的漂移**：平台用自己的 agent 扩展自己的 skill，缺乏闸门会失控（库膨胀、质量下降）。
5. **BYO-Key 的 onboarding 摩擦**：用户要连一堆模型 Key。对策：onboarding 做成"连接模型"步骤，
   能力按已连模型动态点亮，未连能力在创建角色时灰掉并提示。
6. **"自动集成模型"的预期边界**：其真实含义是"系统托管配置 + 按需注入凭证 + 标准接口配置即用"，
   不是"任意模型 API 零代码接入"——要管理好预期。
7. **真实副作用 + prompt 注入（最危险组合）**：带"发布/外发/支付"权限的角色，一旦被检索来的网页内容注入指令，
   后果是真实的。对策：**每角色最小权限 + 危险动作强制人审 gate**（见 5.5），不允许这类动作全自动。
8. **多角色接缝的质量塌方**：上下文交接有损 + 返工无闭环 → 误差累积/空转。对策：角色集内聚校验 + 共享 schema +
   显式返工闭环（4.4）+ 早建评估/打分机制（否则无法判断系统是否在变好）。
9. **生成角色/编配的质量与意图误读**：onboarding 意图理解会读错、生成角色会跑偏。对策：预览 + 小样例验证 + 人审才生效。

## 9. 对标市面与缺口补强（本轮新增）

> 对标 AutoGen / OpenAI Agents SDK / CrewAI / LangGraph / MetaGPT·ChatDev / Devin·Manus /
> Dify·Coze / LangSmith·Langfuse / MCP 等。**我们在治理、BYO 安全、可复现、durable 编排上领先多数开源框架**；
> 但在"**动态自主性、AI-ops、生态对齐**"三方面有缺口。以下 7 条为补强决策。

### 9.1 动态重规划（静态 DAG 太脆）
- 现状：上游规划器出 DAG → 执行；只有人发 signal 改。
- **补**：编排层在**节点失败 / 产出不达验收**时，触发**有界的局部重规划**（重排/插入/替换少量节点），
  仍走人审或自动放行策略；**不是整盘重来，也不是无限自主**。
- 对标：LangGraph 动态分支、Devin/Manus 边做边改。

### 9.2 受控的角色间交接 / 澄清（"绝不直接对话"过刚）
- 现状：角色不直接对话，全部经编排层。
- **补**：保留编排主线，但增加一个**受控原语**——角色可"向某角色提问 / 交接子问题"，
  **仍由编排层记录与调度**（不是自由黑板、不是点对点私聊）。
- 对标：AutoGen / OpenAI Agents SDK 的 handoff。

### 9.3 评估 · 追踪 · 质量闭环（最该补的 AI-ops）
- 现状：只有"公司看板"（看进度）。
- **补**：**Trace**（每步输入/输出/工具调用可回放）+ **Eval**（产出打分 / 回归测试集 / 对比改动前后）。
- 没有它，无法判断系统是否在变好、改 prompt 是变好还是变坏。对标 LangSmith / Langfuse。

### 9.4 工具接 MCP（别自研工具协议）
- 现状：lite-agent + 自研小工具集。
- **补**：**lite-agent 直接消费 MCP(Model Context Protocol) 工具**，复用 MCP 生态（浏览器/文件/各连接器）；
  自研工具仅在 MCP 没有时才写。**skill(手册) 与 MCP(工具) 解耦**：手册讲"怎么做"，MCP 提供"用什么做"。

### 9.5 防护栏 / 注入检测（有风险无机制）
- 现状：只有最小权限 + 人审兜底。
- **补**：数据进 agent 前加一道 **guardrails**——注入检测 / 内容过滤 / PII / 输入输出审查；
  与 5.5(最小权限)、第 8 节风险 7 配合形成**纵深防御**。对标 NeMo Guardrails / Guardrails AI。

### 9.6 记忆检索机制（三层记忆缺"怎么取"）
- 现状：3.11 定义了任务/角色/组织三层，但没说检索。
- **补**：记忆**向量化 + 按相关性 RAG 检索**后注入切片（仍是摘要不是全量）；组织记忆越长越要靠检索而非全注入。
- 对标 MemGPT / Letta 的记忆架构。

### 9.7 SOP + 结构化中间产物 schema（MetaGPT 的关键教训）
- 现状：5.3 提了"共享 schema"，但太弱。
- **补**：把每个场景的角色交接做成**强 schema 的 SOP**——每个中间产物(PRD/数据集/报告草稿…)有明确结构，下游按 schema 读。
- **让"公司"work 的是 SOP + 结构化产物，不是角色人设**。对标 MetaGPT / ChatDev。
